# Digit classifier model

A small CNN that classifies a single cropped, binarized seven-segment digit
(0-9). Used by `classifyDigitWithModel` in `src/app.js`, which crops the
region `recognizeSevenSegmentReading` found for one digit, letterboxes it
into a 32×32 grayscale image (aspect ratio preserved — never stretched to
fill the square), and feeds it to the model. `getDigitModel` loads it once
via `tf.loadLayersModel("/model/digit-classifier/model.json")` and caches
it for the rest of the session.

## Why a trained model instead of a fixed segment-threshold rule

The original approach sampled the seven classic segment regions (a-g) of a
digit box and thresholded each one's ink density. It was fragile against
real photos — glare, blur, tilt, and font-style variation all shift where
segment ink actually falls relative to fixed sampling bands, and every fix
for one real device photo's failure mode surfaced a new one on the next.
A model trained on a wide enough variety of synthetic examples generalizes
far better, without needing another hand-tuned threshold for each new
failure mode. The old function is kept in `app.js` as a zero-dependency
fallback if the model fails to load.

## Architecture

3 conv+maxpool blocks (16→32→32 filters, 3×3 kernels, same padding) →
flatten → dropout(0.3) → dense(64, relu) → dense(10, softmax). Input:
32×32×1 grayscale, ink normalized to ~1 and background to ~0 (inverted
from the app's own black-ink-on-white binarized image). ~194KB as saved
(model.json + weights.bin).

## Training data

Entirely synthetic — generated by drawing seven-segment digits on an HTML
canvas (via headless Chromium/Playwright, since this was built in a
sandbox without real labeled meter photos) with randomized:

- Overall size (50-140px cell width) and aspect ratio, so the model isn't
  tied to one resolution/zoom level.
- Rotation (±~6°) and horizontal shear (±6%), for a photo shot slightly
  off-level.
- `cornerCut`: how mitered each segment's corners are, interpolating
  between a font that draws segments almost fully disconnected (seen on
  a real device's own debug crop earlier in this project) and one with
  barely any gap (a physical LCD's continuous strokes) — both real
  styles encountered against actual photos.
- Mild glare (soft white radial wash, occasional) and blur (0-0.8px),
  simulating photo/JPEG softness.
- Speckle noise (0.2% of pixels flipped) and a randomized binarization
  threshold, rather than a fixed one.

Critically, the crop fed into the final letterboxed 32×32 image is based
on the digit's own **rendered ink extent** (scanned from the canvas after
rotation/shear are applied, not assumed from its nominal cell box), with a
small mostly-outward jitter — matching what the app's real segmentation
pipeline (`findInkComponents` → `mergeInkFragments` → tight bounding box)
actually hands the classifier. Getting this wrong the first time (using
the full cell box, then stretching to fill the square) is exactly what
produced a model that read a real photo's "1" as "2" — see the root-cause
note in the main `README.md`. If this pipeline changes again later
(different erosion radius, merge behavior, etc.), regenerate training data
that matches its new crop tightness rather than assuming this still holds.

## Regenerating / retraining

The generator and training script are not part of the shipped app (they
depend on Playwright and `@tensorflow/tfjs-node`, neither of which the app
itself uses) and were not committed. To rebuild them:

1. A Playwright-driven generator renders labeled digit images as described
   above and writes them to a flat binary file: one `uint8` label byte
   followed by 1024 `uint8` grayscale pixel bytes, repeated per record.
2. A `@tensorflow/tfjs-node` script loads that binary format, builds the
   architecture above, trains for ~18 epochs (Adam, batch size 64,
   categorical crossentropy), and saves via `model.save("file://...")`,
   which produces the `model.json` + `weights.bin` in this folder directly
   in the browser-loadable format — no separate conversion step.
3. Copy the two output files into this folder. `esbuild.config.js` copies
   everything here into `www/model/digit-classifier/` on every build.

Always validate a retrained model against real device photos before
shipping it, not just against held-out synthetic validation accuracy — a
dataset with a systematic bug (as above) can still validate well against
itself while failing in a way that only shows up on a real photo.
